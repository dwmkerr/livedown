## Context

The viewer's `split` mode renders two scroll containers side-by-side inside `<div id="panes">` (see `public/index.html`):

- **Source pane** — `#pane-source` wraps a CodeMirror 5 textarea (`#cm-source`). CodeMirror owns its own scroller; the outer `#pane-source` has `overflow: hidden`. The scrolling element is `cm.getScrollerElement()` (the `.CodeMirror-scroll` div).
- **Preview pane** — `#pane-preview` is a plain `<div>` with `overflow-y: auto`. Inner content lives in `#preview-inner` and is regenerated by `renderPreview()` on every `update`/local push via `marked.parse(content)`.

Today the two panes scroll completely independently. On any document longer than a viewport, reading the rendered preview while watching incoming live edits in the source pane (or vice versa) requires constant manual re-alignment.

Both panes are visible only when `panes.dataset.mode === 'split'`. In `code` mode `#pane-preview` is `display: none`; in `preview` mode `#pane-source` is `display: none`. CodeMirror needs `cm.refresh()` after layout changes — already handled in `applyMode()`.

`marked` exposes a renderer extension API; we can hook the `heading`, `paragraph`, `list`, `code`, `blockquote`, `table`, `hr`, and `html` renderers to stamp the originating source line on the emitted top-level element. The token passed to each renderer carries `token.raw` and a token-level position, and `marked.Lexer` exposes line-aware tokens through `tokens[i].lines` when the lexer is configured with `gfm: true` (the default). For tokens that don't carry their own line, `marked` provides the raw string and we can derive a 0-based source line by walking the cumulative raw lengths during render.

The browser viewer is a single static HTML file; there is no bundler. New JS is plain ES5/ES2015 inline `<script>`, consistent with the rest of `public/index.html`.

## Goals / Non-Goals

**Goals:**
- In `split` mode, scrolling either pane keeps the other pane aligned to the same region of the document.
- "Same region" is defined by a source-line ↔ rendered-block mapping built when the preview is rendered.
- No echo / ping-pong: the inactive pane follows but its programmatic scroll does not re-trigger sync back to the driver.
- Works for every markdown construct currently rendered (headings, paragraphs, lists, fenced code, blockquotes, tables, hr, raw HTML, mermaid diagrams).
- No new dependency, no new protocol message, no relay change, no CLI change.

**Non-Goals:**
- Sub-line precision inside a paragraph. Mapping resolution is at the top-level block level (the unit `marked` emits).
- Cursor-position sync (only scroll position). Showing where a remote editor's cursor is is a different feature (`feat(ui): cursor presence`) not requested in #114.
- Sync in `code` or `preview` modes — only one pane is visible.
- Smooth animated easing of the follower. We jump the follower so it stays correct under fast scrolls; smoothing is a follow-up if needed.
- Persisting scroll position across reloads or across mode toggles.

## Decisions

### 1. Stamp source line on every top-level rendered block via a `marked` renderer hook
Override `marked`'s block-level renderers (`heading`, `paragraph`, `list`, `code`, `blockquote`, `table`, `hr`, `html`) to emit `data-source-line="<n>"` on the outer element. `n` is the 0-based source line where the token starts.

The line number is computed at render time by maintaining a running cursor: walk `marked.lexer(content)` once to get the token list, then track the cumulative number of newlines in `token.raw` to assign each token a start line. This is O(n) over the token stream and runs as part of `renderPreview()`.

For mermaid replacement (existing code in `renderPreview` swaps `<pre><code class="language-mermaid">` for `<div class="mermaid">`), copy the `data-source-line` from the original `<pre>` to the replacement `<div>` so the mapping survives.

Rejected: parsing the raw markdown in JS separately from `marked` (duplicates work, drifts from `marked`'s tokeniser).
Rejected: stamping IDs on every line of source (CodeMirror line widgets) and using them as sync anchors (heavier, and the source side already has line numbers natively via `cm.lineAtHeight()`).

### 2. Build the line map after `renderPreview()`
A `buildLineMap()` function runs at the end of `renderPreview()` and returns a sorted `[{ line, top }]` array where `top` is `element.offsetTop` relative to `#pane-preview`. This is the lookup structure used by both directions of sync.

Cached on the `renderPreview` closure as `lineMap`. Rebuilt on every render (cheap; renders are already debounced 400ms by the editor's `pushTimer`, and remote `update` messages already trigger a single render).

### 3. Bidirectional scroll handlers with a single-shot "driver" lock
Two listeners:
- `cm.on('scroll', …)` on the CodeMirror scroller.
- `pane-preview.addEventListener('scroll', …)`.

A module-level `syncDriver` variable holds either `'source'`, `'preview'`, or `null`. When a handler fires:
1. If `syncDriver` is the *other* pane, return — this scroll event was caused by our own programmatic follow.
2. If `panes.dataset.mode !== 'split'`, return — only one pane is visible.
3. Otherwise set `syncDriver = <this pane>`, compute the target scroll for the other pane, set it via `scrollTop` / `cm.scrollTo`, then schedule `syncDriver = null` via `requestAnimationFrame` so the matching `scroll` event from the follower lands while the lock is still set.

This pattern is well-known for editor↔preview coupling (it's what the VS Code markdown extension does); it avoids debouncing and feels native.

Rejected: time-based debounce ("ignore other-pane scrolls for 150ms"). Fights with momentum scrolling on trackpads and feels laggy.

### 4. Source → preview math: line → top
On a source scroll, read the first fully-visible source line: `cm.lineAtHeight(scroller.scrollTop, 'local')`. Find the two adjacent entries in `lineMap` that bracket that line and interpolate linearly between their `top` values to get a preview `scrollTop`. Set `pane-preview.scrollTop = interpolated`.

### 5. Preview → source math: top → line
On a preview scroll, walk `lineMap` to find the two entries that bracket `pane-preview.scrollTop`; interpolate to get a source line `L`. Use `cm.charCoords({ line: L, ch: 0 }, 'local').top` to get the pixel offset of that line in the CodeMirror scroller, then call `cm.scrollTo(null, top)`.

### 6. Re-sync on mode change
`applyMode()` already calls `cm.refresh()` when switching modes. After switching *into* `split`, re-align once by treating the preview as the driver (because a reader is more likely to have been on `preview` last). This keeps the source pane in step with whatever the user was reading.

### 7. No new dependency
All math uses the existing CodeMirror 5 API (`scrollTo`, `lineAtHeight`, `charCoords`, `getScrollerElement`) and standard DOM (`scrollTop`, `offsetTop`). `marked.use({ renderer })` is already loaded.

## Risks / Trade-offs

- **Lexer drift** — relying on `marked.lexer(content)` to enumerate tokens means a future `marked` version that changes token shape could break the line map. Mitigation: token line tracking uses only `token.raw` and `token.type`, both of which are part of `marked`'s public token API. Unit test on the mapping covers the contract.
- **Jumpy mermaid blocks** — mermaid renders asynchronously and changes `offsetTop` of everything below it after layout. Mitigation: after `window.mermaid.run(...)` resolves (existing code), rebuild the line map. Also rebuild on `window.resize`.
- **Wrap-induced height drift in the source pane** — CodeMirror has `lineWrapping: true`. `charCoords` accounts for wrap, so line→pixel is correct. Soft-wrapped sources stay aligned.
- **Very short documents** — when both panes fit without scrolling, all scrollTop values are 0. The driver lock still applies, no work to do. No regression.
- **`#preview-inner` has top padding** — `offsetTop` of the first block is non-zero; interpolation uses absolute `offsetTop` values so this is correct without extra handling.
- **Programmatic scroll-into-view from existing remote-edit flash** — the flash only adds a border class, not a scroll. No interaction.
- **Code-only or preview-only mode toggle while sync is pending** — guard each handler with the `panes.dataset.mode === 'split'` check. No stray cross-pane writes.

## Migration Plan

Single-PR change, no migration. Feature is live in `split` mode as soon as the HTML ships. To disable, the user can switch to `code` or `preview` mode (no setting needed). No data, no config, no rollback complexity.

## Open Questions

None blocking. A follow-up could add an "anchor under the cursor when typing" mode (keep the preview pinned to where the cursor is, not where the user scrolled) but #114 only asks for scroll sync.
